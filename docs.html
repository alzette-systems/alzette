First call

Quickstart

Ask your project administrator for the workload’s gateway origin, model alias, and a newly issued API key. Do not infer the gateway origin from the public-site or portal port.

Default local origins

Gateway: http://localhost:8080 · Portal: http://localhost:8081/login. A LAN deployment can publish different ports. The portal’s Docs view shows the active gateway origin.

cURL

Environment and request
export ALZETTE_BASE_URL='http://your-gateway-host:8080'
export ALZETTE_API_KEY='alz_k_...'

curl "$ALZETTE_BASE_URL/v1/chat/completions" \
  --fail-with-body \
  -H "Authorization: Bearer $ALZETTE_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "alzette-chat",
    "messages": [
      {"role": "user", "content": "Reply with OK"}
    ],
    "stream": false
  }'

Python with the OpenAI SDK

OpenAI-compatible client
import os
from openai import OpenAI

client = OpenAI(
    base_url=f"{os.environ['ALZETTE_BASE_URL']}/v1",
    api_key=os.environ["ALZETTE_API_KEY"],
)

response = client.chat.completions.create(
    model="alzette-chat",
    messages=[{"role": "user", "content": "Reply with OK"}],
    stream=False,
)

print(response.choices[0].message.content)

Replace alzette-chat with the alias assigned to your project. A provider model slug is operator configuration and is never accepted from the client.

Identity

Authentication

Human access and application access are intentionally different. A portal password must never be copied into application code, and an API key is not a portal password.

Portal username + password

For a person signing in to review company usage, routes, and workload access. It creates a bounded, revocable server-side session.

Used in the browser

Alzette API key

For an application calling the gateway. It is scoped, stored only as a SHA-256 digest, and shown in plaintext once when issued or rotated.

Used as a Bearer token

Store the API key in the application’s secret manager. Rotation creates an overlap; it does not silently revoke the previous key. Revoke the predecessor after the rollout is confirmed. Key names are permanently unique within a service account so retrying an interrupted one-time reveal cannot mint an unnoticed duplicate.

Accepting a quote, opening hosted checkout, or opening billing management may require the person to confirm the current portal password again. That confirmation refreshes only the human session; an application API key is never accepted.

POST /v1/chat/completions

Request contract

The endpoint accepts one JSON object with no query parameters and no unknown fields. The request body is limited to 1 MiB.

FieldRequiredAccepted value
modelYesYour server-authorised Alzette alias, up to 128 characters
messagesYes1–128 bounded entries; text-only system, user, assistant, and validated assistant-tool/tool-result history
streamNofalse for a buffered response or true for the tested text/function-tool SSE subset
stream_optionsNoinclude_usage for a streaming request
temperatureNoNumber from 0 through 2
top_pNoNumber from 0 through 1
max_tokensNoInteger from 1 through 1,000,000
toolsNoBounded function definitions with validated names, descriptions, and object JSON Schemas
tool_choiceNoauto, none, required, or one declared named function

Structured-output controls, embeddings, image/audio content, custom or grammar tools, target URLs, tenant IDs, and provider model slugs are outside this tested contract and fail closed.

Correlation

Responses and request IDs

A successful non-streaming response is buffered and validated before any customer bytes are written. In streaming mode, Alzette validates and flushes supported text and function-tool deltas, requires a supported terminal finish reason and [DONE], and never retries after the first downstream write.

  • X-Alzette-Request-ID identifies the logical customer request.
  • X-Request-ID carries the same identifier for common client tooling.
  • Error bodies repeat it as request_id in a stable JSON envelope.
  • Give that Alzette request ID to support; provider attempts and target details remain operator-only.

Customer evidence

Usage and portal

One authenticated gateway call is one logical request. A bounded retry may create another provider attempt, but it does not become another customer request.

Logical request
The customer-visible unit used by totals, outcomes, latency, attribution, and exports.
Provider attempt
An operator-only delivery attempt. Its URL, credential, provider response body, and retry detail are not exposed through customer APIs.
Token finality
Provider-reported tokens are shown when known. Failed-only periods remain unknown; completed empty periods are not applicable.

The portal separates Overview, Usage, Models, Endpoints, Billing, Access, and Docs. It provides organisation/project/environment scope, model and service-account attribution, latency, throughput, peak concurrency, route and plan evidence, rollup status, and safe CSV/JSON exports.

Zero is a real state

Signing in, browsing, exporting, or managing keys does not create inference usage. Statistics appear only after an application calls the gateway with that client’s scoped API key.

Bearer-only machine views are also available on the control origin: GET /api/v1/dashboard, GET /api/v1/usage, and GET /api/v1/requests/{id}.

Control plane

Models and endpoints

The Models workspace is an organisation-eligible catalogue, not a public model list. Every selectable offer identifies an operator-reviewed release, approved Alzette alias, service profile, evidence/finality, and—when authoritative—fixed price or allowance. A catalogue entry does not prove that a route is ready.

  1. Choose a published shared or dedicated offer and describe the workload. Customers never enter a provider URL, provider model, secret, Stripe object, or raw machine.
  2. Save the server-backed draft or submit it. Stable idempotency keys prevent duplicate configurations, requests, checkout sessions, service accounts, and hidden credentials.
  3. A shared evaluation may bind its allow-listed route immediately. Paid shared service waits for signed payment evidence. Dedicated service waits for quote acceptance, any payment requirement, allocation, deployment, validation, and an evidenced route binding.
  4. Use the endpoint detail to see configuration, commercial, payment, and runtime states independently. A capacity request preserves bounded sizing intent for operator review and changes the deployment behind a ready dedicated endpoint only after quote, payment policy, allocation, and validation; it does not change the customer alias or credential contract.
Stripe is a hosted processor, not the seller

When billing is configured, the customer pays Alzette through Alzette’s Stripe merchant account. The customer does not create or connect a Stripe account, and payment fields never transit the Alzette portal. With billing disabled, paid actions remain unavailable.

Failure contract

Errors

Provider error bodies, credentials, and target URLs are normalized and never returned to the caller.

Current scope

Delivery boundary

The implemented runtime is a PostgreSQL-backed, single-machine Docker Compose PoC. Its configured route is labelled External pilot / Shared pilot. Deterministic compatible-target tests have passed; a live OpenRouter result is not asserted here.

The endpoint catalogue, configuration, quote, billing-state, webhook, and fulfilment ledgers are implemented and deterministically tested. They are not proof that a particular offer, Stripe checkout, provider route, private machine, or capacity profile is currently available.

These items remain outside current evidence: MeluXina access, a deployed private model, private LAN serving, Luxembourg execution or residency, dedicated compute, production capacity, an SLA, live Stripe settlement, scheduled billing reconciliation, structured output, embeddings, multimodal input, public signup/recovery/invitations, SSO, and multi-host orchestration.

MeluXina is the intended production environment. Those claims become current only after access, allocation, networking, model serving, monitoring, recovery, and the customer contract have been validated.
